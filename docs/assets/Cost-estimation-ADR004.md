# Azure State Backend Cost Estimate

## Purpose

This document provides an order-of-magnitude cost estimate for using Azure Blob Storage as the OpenTofu remote state backend.

It supports the architectural decision to prefer Azure Blob Storage while making the cost assumptions explicit and reviewable.

This is not a formal Azure quotation. Actual costs depend on the organisation's Azure agreement, selected redundancy, networking model and usage.

## Scope

The estimate covers the incremental cost of using Azure Blob Storage for OpenTofu state in **West Europe** or **North Europe**.

Included:

- Blob storage capacity;
- Blob read and write transactions;
- state version history;
- Internet egress when OpenTofu runs outside Azure;
- audit logging generated by state access.

Excluded:

- existing Azure platform costs;
- shared VPN or ExpressRoute infrastructure already required for other workloads;
- operational staff costs;
- taxes and organisation-specific Azure discounts.

If a Private Endpoint or dedicated network connectivity is introduced specifically for OpenTofu state, its cost must be evaluated separately.

## Cost assumptions

### Number and size of states

ADR-003 defines one state per combination of deployment scope and environment.

A deliberately generous reference scenario is used:

- 50 deployment scopes;
- 3 environments;
- 150 active states;
- average state size of 2 MB.

This results in approximately:

`150 × 2 MB = 300 MB`

of current state data.

OpenTofu state is normally relatively small because it stores resource metadata and attributes rather than application data.

### State history

State must be recoverable, so version history must be retained.

Assuming an average of 20 retained versions per state:

`300 MB × 20 = approximately 6 GB`

of total stored state data.

Even with deliberately generous assumptions, the storage volume remains very small for an object-storage service.

## Storage and transaction cost

Azure Blob Storage charges for stored capacity and HTTP operations.

For the OpenTofu state workload:

- storage capacity is measured in only a few GB;
- read/write operations happen mainly during `plan`, `apply`, refresh and state-management operations;
- the number of operations is very small compared with typical object-storage workloads.

Azure also lists data retrieval and data writes for Hot block blobs as free per GB; normal request transaction charges still apply.

The resulting storage and transaction cost is therefore expected to remain at the level of cents or a very small number of euros per month.

Because Azure pricing varies by account type, redundancy and commercial agreement, this document intentionally does not hard-code a precise storage price.

## Network traffic

### Ingress

State written from an on-premises runner to Azure is inbound traffic to Azure.

Azure does not charge for Internet data ingress.

The expected ingress cost for OpenTofu state is therefore:

**EUR 0 for bandwidth ingress.**

### Egress

When OpenTofu runs on-premises, state reads travel from Azure to the local runner and are Internet egress from Azure.

West Europe and North Europe fall under Azure's European Internet-egress pricing.

At the time of this estimate, Microsoft lists **USD 0.087 per GB** for the first charged 10 TB/month routed via the Microsoft Premium Global Network.

Azure provides a global free egress allowance, but this estimate **does not allocate any part of that allowance to OpenTofu**, because other organisational Azure workloads may already consume it.

A conservative calculation is therefore:

| Monthly state egress | Approximate bandwidth cost |
| ---: | ---: |
| 10 GB | USD 0.87 |
| 20 GB | USD 1.74 |
| 50 GB | USD 4.35 |

These volumes are already generous for OpenTofu state traffic.

For example, with 150 states averaging 2 MB and 20 complete state reads per month:

`150 × 2 MB × 20 = approximately 6 GB/month`

At the current published rate:

`6 GB × USD 0.087 = approximately USD 0.52/month`

This calculation deliberately assumes that all OpenTofu egress is chargeable.

## Audit logging

State access must be auditable.

Audit logs may remain in Azure and do not need to be continuously exported on-premises.

The state workload generates a small number of storage operations, so the corresponding diagnostic-log volume is expected to be low.

If the organisation already uses Azure Monitor / Log Analytics as a shared logging platform, the marginal cost attributable specifically to OpenTofu state should remain small.

Audit-log retention requirements may influence this cost more than the state workload itself.

## Networking considerations

The simplest architecture can access Azure Blob Storage over secured HTTPS using Azure identity and access controls.

If a Private Endpoint is required, additional costs apply for the Private Endpoint and processed traffic.

Likewise, VPN or ExpressRoute connectivity has its own cost model.

These network services should only be attributed to the OpenTofu state backend when they are introduced specifically for this use case. If they already exist as part of the Azure landing zone, only their incremental cost should be considered.

## Expected cost range

Based on the expected state volume and access pattern:

- storage capacity: negligible;
- storage transactions: negligible;
- ingress: no bandwidth charge;
- egress: typically well below a few USD/EUR per month;
- audit logging: low incremental volume;
- dedicated networking: excluded unless required specifically for state.

A reasonable planning assumption for the **core Azure state backend** is therefore:

> **A few euros per month under normal use, excluding dedicated networking services.**

The estimate remains conservative because it assumes that OpenTofu receives none of Azure's free monthly Internet-egress allowance.

## Architectural conclusion

Direct Azure consumption cost is not expected to be a significant factor in the backend decision.

The more important trade-off is between:

- the low operational overhead and existing organisational integration of Azure Blob Storage; and
- the greater infrastructure autonomy of operating an on-premises state backend.

Because the state remains small and OpenTofu supports migration between backends, Azure Blob Storage provides a low-cost preferred solution while preserving the possibility of moving to an on-premises alternative later.
